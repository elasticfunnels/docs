ElasticFunnels can serve your site in several languages. There are two ways to
build it, and one brand can use both:

| | Linked pages | Dictionary page |
| --- | --- | --- |
| What you make | One page per language (`about`, `ro/despre`, `es/acerca`) | One page for every language (`about`) |
| Where the words live | In each page's own HTML | In the brand dictionary, as keys: `{{ t('hero.title') }}` |
| URLs | Each page's own slug, so slugs can be translated | `/about`, `/ro/about`, `/es/about` with prefix routing on |
| SEO fields, layout, images | Their own per language | Shared; only the texts change |
| Best for | Sales pages, articles, anything where the copy, offer or layout differs by market | Checkouts, members pages, shared navigation, pages whose layout never changes |

Either way, a page in a language renders in that language, gets
`<html lang>`, reciprocal `hreflang` links, a self canonical and sitemap
alternates, and can show a language switcher and a "this page is also in
Romanian" prompt. See [SEO for multilingual sites](/pages/seo#multilingual-sites-hreflang)
and [Language prompt and switcher](/pages/language-prompt).

Nothing changes for a brand that does not use it: a page without a language
renders exactly as before.

## Set up your languages

Both models start with the brand's languages. Open **Pages → Advanced →
Translations**.

<img src="/images/pages/i18n-languages.png" alt="The Languages list in Pages, Advanced, Translations: English marked Default with the / prefix, Español under /es/ and Română under /ro/, with the Add language button and the edit icon on each row" />

<Steps>
  <Step title="Add a language">
    Click **Add language** and enter:

    | Field | What to put |
    | --- | --- |
    | **Code** | A short language code: `en`, `de`, `ro`, `pt-br`. Stored in lowercase. |
    | **Language** | The name visitors see in the language switcher and the prompt. Write it in its own language: `Română`, `Deutsch`, `Português (Brasil)`. |
    | **Default language** | The language a page without one is in, and the one shown when a visitor's language has no version. One per brand. |
    | **Sort order** | Order in the switcher and in language lists. |
    | **URL prefix** | The path prefix for prefix routing. Leave it empty to use the code (`/pt-br/`); the default language has no prefix. Lowercase letters, digits and dashes. |
  </Step>
  <Step title="Add the default language too">
    Add your main language (usually `en`) and switch on **Default language**.
    Without it, ElasticFunnels cannot tell which version is the main one for
    `hreflang="x-default"` or for text fallbacks.
  </Step>
</Steps>

<Note>
Codes are matched exactly. `pt` and `pt-br` are two languages: add both if you
need both. A language that pages or components use can't be deleted or have
its code changed; the error says how many use it.
</Note>

## Linked pages: one page per language

Each language version is its own page with its own slug, HTML, SEO title and
description, revisions and split tests. One page is the **original**; the
others are its **translations**. Together they are a translation group. The CLI
calls the original the source.

### Give the original its language

Open the original page's settings and the **Language** tab. Set **Page
language** to the language it is written in. **Not set** keeps the page as it
was before languages existed.

<img src="/images/pages/i18n-page-language-tab.png" alt="Page settings, Language tab of the original page: Page language set to English, the Translations panel listing the English original and the Romanian translation, and the Add translation in, URL and Add translation controls for Español" />

### Make a translation

In the **Translations** panel on the same tab, pick a language in **Add
translation in**, check the **URL**, and click **Add translation**.
ElasticFunnels makes a draft copy of the original in that language, links the
two, and proposes the URL `<prefix>/<original slug>`:

| Original slug | New Romanian page | Answers at |
| --- | --- | --- |
| `about` | `ro/about` | `/ro/about` |
| `index` (the homepage) | `ro/index` | `/ro` |
| `blog/sleep-tips` | `ro/blog/sleep-tips` | `/ro/blog/sleep-tips` |

Change the URL to a translated one if you want (`ro/despre`). Then translate
the copy, the SEO title and description, and publish the page. If the brand
has no languages yet, the panel says **Add your languages first.** with a link
to **Go to Translations**.

The panel lists every version: **Original**, **(this one)** for the page you
are on, the language of each, and links to **Open the page** and **Open its
settings**.

With the CLI:

```bash
ef pages translate about --lang ro                 # creates ro/about and pulls pages/ro/about.ef
ef pages translate about --lang es --slug es/acerca --title "Acerca de"
ef pages translations about                        # every version, with its status
```

### Link pages you already have

If the Romanian page already exists, link it instead of copying. This is done
with the CLI:

```bash
ef pages settings ro/despre --lang ro --translation-of about
ef pages settings ro/despre --translation-of none     # unlink it
ef pages settings about --lang en                     # give the original its language
```

A linked page's **Language** tab names its original, for example **This page
is a translation of About.** Click **Unlink** and save to take it out of the group; it keeps
its content and language.

Rules:

- A group has at most one page per language.
- One level only: a translation's original is never itself a translation. Link
  every translation to the same original.
- An original with no language counts as the default language.
- Unlinking or deleting a translation leaves the other pages as they are.
  Deleting the original makes its first translation the new original.

### When the original changes

A translation remembers the text of its original at the moment it was made or
last marked up to date (the SEO title, the SEO description and the page's
visible text; markup, scripts and styles do not count). When the original's
text changes, the translation shows **Out of date** in the **Translations**
panel.

Update the translation, then click **Mark up to date**. In the CLI, `ef i18n check`
lists every stale and missing translation and exits with an error when one is
stale, so you can use it before you publish:

```bash
ef i18n check --lang ro,es
ef i18n synced ro/about
```

### Components in a language

A page in Romanian that includes the `header` component uses the Romanian
translation of `header` when there is one, and the base `header` otherwise.
Make a component translation the same way as a page translation, from the
component's **Translations** panel (it asks for a **Code** instead of a URL), or
with the CLI:

```bash
ef components translate header --lang ro
```

You can also keep one component for every language and write its texts as
`{{ t('nav.home') }}`. Those follow the page's language too (see below). Pick
by what differs:

| Use | When |
| --- | --- |
| One component with `t()` keys | Only the words change. One place to edit the markup. |
| A translation of the component | The layout, the links or the images differ by language. |

For links in shared navigation, use `page_url('<slug>')` instead of writing
the path. It returns the URL of that page's translation in the current page's
language, and the page itself when there is no translation:

```html
<nav>
  <a href="{{ page_url('index') }}">{{ t('nav.home') }}</a>
  <a href="{{ page_url('features') }}">{{ t('nav.features') }}</a>
  <a href="{{ page_url('pricing') }}">{{ t('nav.pricing') }}</a>
</nav>
```

On `/ro/despre` this links to `/ro`, `/ro/features` and `/ro/pricing` when
those translations exist.

### Funnels keep the visitor's language

When a funnel step or a `/page?id=` link sends a visitor to a page that has a
translation in the language of the page they are on, they land on that
translation. Build the funnel once, with the original pages.

## Dictionary pages: one page, texts per language

A dictionary page is one page for every language. Its texts are keys, and the
brand dictionary holds one value per language.

### Add texts

The **Texts** section of **Pages → Advanced → Translations** lists every text
in every language, with a **Language** column. Pick a language in the filter to
see one.

<img src="/images/pages/i18n-texts.png" alt="The Texts list under Translations on All languages: each key with its language code and text, the Language filter, search, Bulk edit and Add text" />

1. Click **Add text**.
2. Pick the **Language**. It starts on the brand's default language.
3. Enter a **Key** (for example `hero.title`) and the **Text**, then save.

If you save a text in a language the list is not showing, the list switches to
**All languages** so you can see it.

Keys use dot notation to group related texts: `hero.title`, `checkout.cta`,
`faq.refund_policy`. Use letters, numbers, underscores and dots. The same key
repeats in every language: that is how ElasticFunnels knows the English
`hero.title` and the Romanian `hero.title` are the same text.

**Bulk edit** opens a spreadsheet-style editor for one language at a time. If
the list is on **All languages**, it switches to the default language first.
Add or change many keys, then click **Save all changes**. The batch saves
together: if a row fails, nothing is saved.

With the CLI, the dictionary is one JSON file per language:

```bash
ef translations pull       # writes translations/en.json, translations/ro.json, ...
ef translations push       # sends your edits back
```

```json
{
  "language": { "code": "ro", "label": "Română", "is_default": false, "sort_order": 1, "url_prefix": null },
  "entries": {
    "hero.title": "Somn mai bun din prima săptămână",
    "nav.home": "Acasă"
  }
}
```

### Use texts in a page

```html
<h1>{{ t('hero.title') }}</h1>
<h2>{{ 'hero.subtitle' | t }}</h2>
<img src="/hero.png" alt="{{ t('hero.alt') }}" />
<span data-ef-hl="cta.buy">Buy now</span>
```

| Function or filter | What it does |
| --- | --- |
| `t(key, params?)` | The text for the page's language. Async. |
| `expr \| t` and `expr \| t:params` | Same as `t()`, with the key as the expression. |
| `data-ef-hl="key"` | Replaces the element's text with the key's text in the page's language. |
| `getTranslations()` | The whole `key → text` map for the page's language. Async. |
| `getTranslation(key)` | The text from the brand dictionary only, `''` when missing. |
| `getResolvedLanguage()` | The language code the page renders in (`pt-br`). Async. |
| `locales()` | The brand's language codes, in sort order. Async. |
| `defaultLocale()` | The default language code. Async. |
| `{{ locale }}` | The language code the page renders in. |

**A missing text falls back.** `t()` and `| t` look in the page's language,
then the default language, then ElasticFunnels' built-in texts, and finally
show the last part of the key (`hero.title` shows `title`). `data-ef-hl` uses
the default language's text, then keeps the element's own markup.
`getTranslation()` returns `''` when no language has the key. So a key only
needs a value in the languages where it differs, and visitors never see a raw
key such as `hero.title`.

### Prefix routing

In **Pages → Advanced → Translations**, under **Language URLs**, switch on
**Serve pages under language folders** (prefix routing), or run
`ef i18n settings --prefix-routing on`. Then a request for
`/<prefix>/<slug>` serves the dictionary page `<slug>` in that language:

<img src="/images/pages/i18n-language-urls.png" alt="The Language URLs settings under Translations: the Serve pages under language folders switch, Language suggestion set to Built-in prompt, and Fallback language for search engines" />

| URL | Serves | Language |
| --- | --- | --- |
| `/about` | `about` | the default language (`?hl=` still switches it, without language tags) |
| `/ro/about` | `about` | Romanian |
| `/es` | the homepage | Spanish |

A real page always wins: if a page with the slug `ro/about` exists, `/ro/about`
serves it. Prefix routing only applies to pages without a language; a linked
page in a language is served at its own slug. Each prefixed URL has its own
canonical, and gets `hreflang` and sitemap alternates like a linked page.

### Using translations in backend scripts

Backend scripts (`<script scope="backend">`) have the same helpers, all async:

```javascript
var code = await getResolvedLanguage();
var langs = await getLocales();
var def = await getDefaultLocale();
var dict = await getTranslations();
var cta = await t('checkout.cta');
```

There is no pipe filter in backend scripts: use `await t('key')`. See
[Backend scripts → Data functions](../backend-scripts/data-functions).

## Which language a page renders in

1. **The page's language.** A page with a language always renders in it,
   whatever the visitor's browser or a `?hl=` parameter says.
2. **The URL prefix**, for a dictionary page served under prefix routing.
3. For a page with neither, the old order still applies, first match wins:
   a `hl` or `locale` placeholder in a [wildcard route](/pages/wildcard-routes)
   (such as the slug `docs/{hl}`), then `?hl=`, `?locale=` or `?lang=`, then the
   visitor's session, the domain's and the brand's language setting, the
   browser's `Accept-Language`, and finally the default language.

The result is matched to a brand language exactly. When nothing matches, the
default language is used.

<Warning>
A slug cannot start with a placeholder, so `{hl}/about` never matches a URL.
For `/ro/about`, make a linked page with the slug `ro/about`, or turn on
prefix routing for a dictionary page.
</Warning>

`?hl=` keeps working on pages without a language, which suits checkouts that
need the visitor's language from the page before. It gives one URL for every
language, so search engines can index only one version: use linked pages or
prefix routing for pages you want found in search.

## Template variables

Every page in a translation group, and every page served under a prefix, has
these in its template:

| Variable | What it holds |
| --- | --- |
| `page_language` | The page's language code (`ro`). |
| `default_language` | The brand's default language code. |
| `translations` | One entry per language the page exists in: `code`, `hreflang`, `name` (the language's label), `url`, and `current` (true for this page). |

A switcher written in the template:

```html
<nav aria-label="Language">
  @foreach(tr in translations)
    <a href="{{ tr.url }}" hreflang="{{ tr.hreflang }}" lang="{{ tr.code }}"
       @if(tr.current) aria-current="page" @endif>{{ tr.name }}</a>
  @endforeach
</nav>
```

The [Language prompt and switcher](/pages/language-prompt) page has a switcher
that fills itself in, and the prompt that suggests a visitor's language.

## Permissions

Languages and texts follow the **Translations** permissions in your role:
`view`, `create`, `update`, `delete`. Page translations follow the **Pages**
permissions.

## Patterns and pitfalls

- **Set a default language** before you link pages, so `x-default` and the
  text fallback have a target.
- **Keep keys stable.** Renaming a key in the dictionary does not change your
  templates. Rename only when the meaning of the text changes.
- **Do not redirect by language in a script.** Search engines crawl mostly
  from the US with no `Accept-Language`, so a redirect hides your other
  versions. The [language prompt](/pages/language-prompt) suggests instead.
- **Keep a translation offline until it is ready.** A page with the status
  draft still answers on its live URL, and a new translation starts as a draft
  copy of the original's text. `ef pages settings ro/about --status offline` hides it;
  set it to published when the copy is translated.
